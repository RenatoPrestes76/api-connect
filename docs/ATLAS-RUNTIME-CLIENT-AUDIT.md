# ATLAS Runtime Client — Audit & Architectural Decision (46.20-B)

Read-only inventory of the two existing enrollment-capable apps
(`apps/agent`, `apps/runtime-installer`) against the real, already-tested
Ed25519 `runtime-registration` protocol in `apps/api`, done before writing
any client code — per REGRA ZERO. Every claim below is sourced from reading
the actual code, not from prior documentation.

## `apps/agent` ("Sentinel")

1. **Responsibility**: `package.json` description — "Secure edge agent for
   connecting customer environments to the Seltriva Connect Platform."
   Structurally almost entirely type-only scaffolding (`export type {...}`
   across `bootstrap`/`security`/`connectors`/`sync`/`scheduler`/`health`/
   `telemetry`/`updates`/`plugins`/`cli`/`logs`/`services`/`runtime`) — the
   only concrete implementation is `AgentBootstrapperImpl`/`createAgent()`
   in `src/bootstrap/bootstrapper.ts` (629 lines), a real 7-phase startup
   sequence (config → security → services → connectors → scheduler →
   plugins → ready).
2. **Enrollment protocol**: a single unauthenticated-by-signature call,
   `POST {SELTRIVA_CLOUD_URL}/api/v1/agents/register` with
   `Authorization: Bearer {SELTRIVA_AGENT_TOKEN}` (a static, pre-issued
   token — not exchanged, not derived from a keypair). Lands at
   `apps/api/src/routes/v1/agents.ts`, a different module from
   `runtime-registration`.
3. **Identity**: `config.agent.id` — `process.env.SELTRIVA_AGENT_ID ??
randomUUID()`. No keypair of any kind.
4. **Credential storage**: none beyond the env var itself
   (`SELTRIVA_AGENT_TOKEN`) — no local keyfile, no encrypted store (the
   `security.credentials.encryption_key_path` config field exists but is
   unused — nothing in `bootstrapper.ts` reads or writes it).
5. **Communication**: plain `fetch()`, one call site, no retry, no
   abstraction — a raw `fetch` inside `_registerWithCloud()`.
6. **Reusable HTTP client**: no.
7. **Lifecycle**: yes — real, working 7-phase bootstrap with graceful
   shutdown types (`AgentRuntime` interface) though the _implementation_ of
   signal handling/PID management described by that interface doesn't
   exist yet either (only the interface in `src/runtime/index.ts`).
8. **Heartbeat**: none implemented.
9. **Discovery**: none implemented.
10. **Job execution**: none implemented.
11. **Retry**: none implemented (registration is a single best-effort
    attempt, failure is caught and logged as a non-fatal warning).
12. **Replay protection**: n/a — no signing at all.
13. **Ed25519 support**: none.

## `apps/runtime-installer`

1. **Responsibility**: `package.json` description — "bootstraps an Atlas
   runtime agent on a target machine" — an interactive/CLI _installer_, not
   a long-running Runtime process itself.
2. **Enrollment protocol**: `POST {apiBaseUrl}/api/v1/activate` with a
   plain opaque `activationToken` string (format-validated, not
   cryptographic) — `src/activation/registration.ts`. Response is
   `RuntimeCredentials { runtimeId, companyId, environment, runtimeToken,
heartbeatUrl, syncUrl }` — a bearer-style `runtimeToken`, not a
   certificate.
3. **Identity**: none generated by the installer itself — `machineId` is
   supplied by the caller (presumably read from the host OS), no keypair.
4. **Credential storage**: `packages/agent-identity` ("ARGUS — Atlas Agent
   Identity Foundation") defines domain types/repository _contracts_ only
   (`src/index.ts` is the sole file) — no concrete storage implementation
   found in this package or wired into the installer.
5. **Communication**: `src/utils/http-client.ts`'s `postJson()` — a small,
   real, reusable helper (unlike apps/agent), but built around this
   token/response shape, not Ed25519 signing.
6. **Reusable HTTP client**: yes, `postJson()`/`HttpError`, but
   protocol-specific to the token exchange, not signature-based.
7. **Lifecycle**: no — it's a one-shot CLI activation step, not a running
   process with a lifecycle.
8. **Heartbeat**: a `heartbeatUrl` is returned by activation, but no code
   in this app calls it — the installer's job ends at activation.
9. **Discovery**: none.
10. **Job execution**: none.
11. **Retry**: none found in `registerRuntime()` itself.
12. **Replay protection**: n/a.
13. **Ed25519 support**: none.

## The real, tested protocol (`apps/api`'s `runtime-registration` + `erp-metadata`)

Traced directly from `apps/api/src/modules/runtime-registration/signature.ts`,
`apps/api/src/routes/v1/runtime-registration/{register,heartbeat,auth}.ts`,
`apps/api/src/routes/v1/erp-metadata/runtime.ts`, and the existing
`enrollment-discovery-e2e.test.ts` (the only current caller). This is
**not** the generic `METHOD/PATH/NONCE/BODY_SHA256` + `X-Runtime-*` header
scheme this sprint's brief assumed — the actual, already-shipped protocol
is simpler and body-based:

- **`POST /runtime/register`** — no signature required (identity doesn't
  exist yet). Body: `{organizationCode, activationKey, runtimeVersion,
fingerprint, publicKey (SPKI PEM), hostname, os, architecture?,
capabilities?}`. Response `201`: `{runtimeId, certificate,
organizationId, capabilities, pollingInterval, heartbeatInterval, ...}`.
- **`POST /runtime/heartbeat`** — body-embedded signature, no headers at
  all. Canonical string to sign:
  `JSON.stringify({runtimeId, version, memory, cpu, status: status ?? null, timestamp})`
  (exact key order), signed with `crypto.sign(null, Buffer.from(payload),
privateKeyPem)` (Ed25519's null-digest form), base64-encoded, sent as
  `signature` in the same JSON body. Replay protection is **timestamp
  window (±5 min) + exact-signature dedupe** — there is no separate nonce
  field in this protocol.
- **`POST /runtime/auth/token`** — same signing pattern, canonical string
  `JSON.stringify({runtimeId, timestamp})`. Returns a JWT
  `{accessToken, refreshToken, expiresIn}` (15 min access token, per
  `RUNTIME_ACCESS_TOKEN_TTL_SECONDS`).
- **`GET /erp-metadata/runtime/jobs`** / **`POST /erp-metadata/runtime/result`**
  — a **different, parallel auth mode**: plain `Authorization: Bearer
<accessToken>` from the step above (`requireRuntimeAuth` middleware), not
  per-request signing. `result`'s `schema` field is typed
  `DatabaseSchema` (from `@seltriva/database-sdk`, i.e. GENESIS's own
  output type) — the server adapts it (`services/discovery-adapter.ts`)
  and runs it through ATHENA (`DatabaseScanner` from
  `@seltriva/database-intelligence`) inside `erp-metadata-store.ts`'s
  `reportSchema()`.
- **Tenant/organization**: resolved server-side from `organizationCode` at
  registration into `organizationId`; enforced on every later call
  (`RUNTIME_MISMATCH`/`RUNTIME_ORGANIZATION_MISMATCH`) — the client never
  supplies or chooses it beyond that first registration call.
- The "organization" this protocol operates against is `portal-identity`'s
  organization (`POST /api/v1/portal/auth/register`), a third,
  still-separate concept from both the 46.19 Prisma-backed Control Plane
  Organization and `apps/agent`'s cloud registration — pre-existing, not
  something this sprint should unify.

## Decision (Fase 3)

**Option A — extend `apps/agent`.** `apps/agent` is the one that
conceptually _is_ the Runtime (its own description says so) and has a real
process lifecycle to hang a new capability off of. Neither existing app
implements any part of the Ed25519 protocol, so "adapting" either
necessarily means writing the actual signing/registration/discovery/job
logic from scratch either way — the only real choice is _where that new
code lives_. Extending `apps/agent` keeps it inside an app whose job is
already "be the thing that runs on a customer's machine and talks to
Atlas", rather than creating a fourth application or a standalone script
with no home (both explicitly PROIBIDO/out of scope).

`apps/runtime-installer` was not chosen: it's structurally a one-shot CLI
activation tool with no ongoing process, no heartbeat loop, nothing to
attach a discovery/job-execution loop to without turning it into something
it isn't.

**What "extend" means concretely, and what it doesn't**: `apps/agent`'s
_existing_ `_registerWithCloud()` call (`/api/v1/agents/register`, static
bearer token) is untouched — it's a different, already-working protocol
serving a different route, and this sprint's constraint is "não alterar o
protocolo Ed25519 da API para facilitar o cliente", not "replace whatever
enrollment already exists." A new, additive module,
`apps/agent/src/atlas-runtime-client/`, implements the real Ed25519
protocol and is wired into the bootstrap's Phase 7 as a second, independent,
opt-in registration path (gated by its own env vars, `ATLAS_API_URL` /
`ATLAS_ORGANIZATION_CODE` / `ATLAS_ACTIVATION_KEY` — unset means "skip",
exactly like the existing `SELTRIVA_CLOUD_URL` gate, non-fatal on failure).
No file under the old cloud-registration path was modified.

**Heartbeat mechanism (Fase 10)**: the client uses `runtime-registration`'s
own heartbeat (`POST /runtime/heartbeat`) — the one this protocol actually
defines and the server's own `runtimeHeartbeatHandler` reacts to (promotes
`REGISTERED`→`ACTIVE`). It does **not** touch `apps/api/src/routes/v1/atlas/heartbeat.ts`
(the older `@seltriva/agent-observability`-backed ONLINE/STALE/OFFLINE
mechanism, itself associated with the _other_ agent-identity/agent
concept) — merging the two remains a real architectural decision bigger
than this sprint, exactly as ATLAS 46.20's report flagged, and is not
attempted here.

**GENESIS/ATHENA (Fase 7)**: the client uses `@seltriva/database-sdk`'s
real `PostgresDriver` (GENESIS) to perform an actual `readSchema()` against
a real, reachable Postgres — no fixture, no fake data — and submits that
real `DatabaseSchema` as the job result. ATHENA classification
(`DatabaseScanner`) already runs server-side inside `erp-metadata-store.ts`
on any real schema submitted this way; nothing was duplicated or
reimplemented client-side.
