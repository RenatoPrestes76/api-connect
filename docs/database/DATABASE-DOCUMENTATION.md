# Atlas — Database Documentation

Produced by the ATLAS Master Documentation & Security Audit. Every claim
below comes from direct inspection of `packages/database/prisma/schema.prisma`
(1,301 lines, 41 models) and the two migrations physically applied in
`packages/database/prisma/migrations/`, cross-checked against which models
each `apps/api/src/modules/*` and `apps/api/src/services/*` file actually
reads/writes via a real `prisma.<model>.*` call (not inferred from naming).

**Scope note**: `apps/cloud` maintains its own, separate
`apps/cloud/prisma/schema.prisma` (28 models, a strict subset of the 41
below by name) against its **own separate database** (`seltriva_cloud`,
confirmed via `apps/cloud/.env.example`'s `DATABASE_URL`/`DIRECT_URL`,
distinct from `apps/api`'s `seltriva_connect`). `apps/cloud` is a
different product outside this Atlas audit's scope; it is mentioned here
only where it clarifies why two schema files with overlapping model names
exist in this monorepo.

## Migrations

| Migration                                 | Content                                                                                    | Destructive statements                                                |
| ----------------------------------------- | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| `20260824000000_init_baseline`            | Full baseline — all models except `RuntimeRegistration`                                    | None (`DROP TABLE`/`DROP COLUMN`/`TRUNCATE`/`DELETE FROM`: 0 matches) |
| `20260828004554_add_runtime_registration` | Adds `RuntimeRegistration` model + `RuntimeRegistrationStatus` enum + FK to `Organization` | None                                                                  |

Both migrations are purely additive. `packages/database/prisma/migrations/migration_lock.toml` pins the provider to `postgresql`. No `db push`-only (unrevisioned) schema drift exists — every model in the schema has a corresponding `CREATE TABLE` in one of the two migrations above (confirmed: the July 2026 architecture audit found **zero** migrations directories existed at that time — this has since been corrected).

## Relationship & integrity notes

- **Cascade behavior is deliberate and consistent**: hierarchical, org-owned data (`Workspace`, `Environment`, `Agent`, `ApiKey`, `Deployment`, `OrganizationPlugin`, `License`, `RuntimeAlert`, `ErpIntegration`, `OrganizationMember`) all cascade-delete with their parent `Organization`. `Tenant → Organization` deliberately uses `onDelete: SetNull`, not cascade — deleting a Tenant orphans (not destroys) its Organizations, matching the documented `PENDING_TENANT_ASSIGNMENT` state design (an Organization with no Tenant is a valid, honest state, not an error).
- **Soft deletes**: `Tenant`, `Organization`, `User`, `OrganizationMember`, `Workspace`, `Environment`, `Agent` (via `retiredAt`), `Plugin`, `AtlasAdminUser` all carry a nullable `deletedAt`/`retiredAt` rather than a hard delete. Confirmed in application code: `OrganizationService.softDelete()` sets `deletedAt` + `status: 'DELETED'`, never calls `.delete()`.
- **Tenant isolation at the schema level**: every tenant-owned table carries an explicit `organizationId` (or `tenantId`) foreign key and a matching `@@index`. The schema itself enforces referential integrity; whether every _route_ correctly filters by it is a separate, application-layer question — see `docs/security/SECURITY-AUDIT.md` for the two real gaps found and fixed in this audit (Finding SEC-002) where the ownership check was missing at the route layer despite the FK existing at the schema layer.
- **No raw SQL / query builders bypassing Prisma** were found in any of the 37 audited business modules — the two Postgres-backed modules (`control-plane`, `runtime-registration`) both use Prisma's typed query API exclusively, plus one `prisma.$transaction` each for check-then-act sequences (`tenancy.repository.ts`'s `createOrganization`/`updateOrganization`).

## The "in-memory by design" reality

**29 of the 41 models above have zero runtime consumer** — a real, load-bearing fact for anyone assuming this schema reflects what Atlas actually persists today. This is not evidence of abandoned migrations; it reflects a consistent, repo-wide convention (documented explicitly in `docs/ATLAS-46.19-CONTROL-PLANE-PERSISTENCE.md` and reconfirmed by this audit's module-by-module inventory in `docs/ARCHITECTURE.md`): most of the 37 business-logic modules under `apps/api/src/modules/` were built with an in-memory store first, with the Prisma schema declared ahead of time as the intended future persistence layer, per-module, on an as-needed basis. Two modules (`control-plane`'s Tenant/Organization, `runtime-registration`'s RuntimeRegistration) and one attribute of a third (`admin-identity`'s AtlasAdminUser, fixed in this audit) have actually made that jump so far.

**Practical consequence, confirmed by direct testing in this audit**: every one of the following resets to its seed/empty state on every `apps/api` process restart — admin sessions/login-attempts/audit-log, all of `security`, `governance`, `ha`, `billing`, `marketplace`, `helios`, `prometheus`, `observatory`, `operations`, `orchestrator`, `job-orchestration`, `message-delivery`, `erp-connectivity`, `erp-metadata`, `query-execution`, `query-planner`, `sql-generator`, `semantic-mapping`, `canonical-model`, `connectors`, `connector-management`, `fleet-ops`, `gateway`, `regions`, `release`, `titan`, `workflow-builder`, `chaos`, `ai-copilot`, `onboarding`, `runtime-connector-execution`, `portal`, and `portal-identity`'s own organization/user/environment/invite records (though the latter's `Organization`/`Tenant` link is durable via `control-plane`). `docs/deployment/production-environment-contract.md` and prior ATLAS production-readiness sprints already establish that `apps/api` can restart at any time on a hosting platform (redeploy, crash, or free-tier idle spin-down) — this is a materially important operational fact for anyone treating Atlas as production-ready for the domains above.
