## Resumo executivo

**Não, os erros encontrados não foram "todos corrigidos e mesclados".** Em detalhe:

1. **Mesclados: não, nenhum.** `git merge-base --is-ancestor sprint-a2.6-secure-config master` → `NOT MERGED INTO MASTER`. Os 19 commits da Sprint A2.5/A2.6 inteira ainda estão só na branch.
2. **Corrigidos: a maioria sim, mas 4 correções reais ainda estão só no working tree, nem commitadas.** `git status` mostra `apps/runtime-installer/src/index.ts`, `.../service-manager.ts`, `.../windows-service.ts` e `.../windows-service.test.ts` modificados e não commitados — e o diff mostra que são exatamente correções de bugs achados "durante o smoke test em VM da Sprint A2.6" (comentários no próprio código citam isso literalmente).
3. **Uma correção é um contorno, não uma causa raiz resolvida.** O erro "serviço instalado mas falha ao iniciar logo após o install" foi contornado com uma mensagem pedindo para o operador abrir um terminal novo e rodar `Start-Service AtlasRuntime` manualmente (`index.ts`, diff não commitado) — o próprio comentário admite: _"The fix is a new process, not more patience from this one"_. Não é uma correção de código, é uma instrução operacional.
4. **O roteiro formal (`docs/ATLAS-SMOKE-TEST.md`) nunca foi executado e preenchido de ponta a ponta.** A tabela "Resultado" no fim do documento está com todos os 13 itens em `☐ OK ☐ Falhou` — nenhum marcado. Em resumo: **houve teste real contra uma VM/execução real** (os erros abaixo são concretos, com mensagens de erro reais, não hipotéticos) — mas o processo está **inacabado**: parte das correções não está nem commitada, nada está mesclado, e não existe um registro de que o roteiro completo passou de ponta a ponta.

## Parte 3 — Confirmação do que ainda não existe

### 3.1 Leitura de dados reais do ERP (Sprint A3)

**Confirmado: não existe.** "Sprint A3" não aparece em nenhum lugar do repositório (busca vazia em todo `API_Connect`).

- `executeDiscoveryScan()` (`apps/agent/src/atlas-runtime-client/executor.ts`) chama só `driver.readSchema()`.
- `DatabaseSchema` (`packages/database-sdk/src/schema/metadata.ts`) carrega nome/colunas/tipos/relações de tabelas — nunca valores de linha.
- O próprio `docs/ATLAS-SMOKE-TEST.md` (item 7, linhas ~483-496) já documenta isso explicitamente: _"isto prova que o runtime leu de verdade a estrutura real do micro ERP [...] mas o produto específico cadastrado [...] não viaja até o Atlas hoje; só a existência/estrutura da tabela onde ele mora [...] seria uma funcionalidade nova, fora do escopo deste roteiro."_

Ou seja: o produto hoje prova leitura de **esquema**, nunca de **dados**. Ler valores de linha reais do ERP (Sprint A3, no sentido que a pergunta levanta) é trabalho futuro, não iniciado.

### 3.2 Persistência de organizações e chaves de ativação

**Confirmado: ambos ainda em memória**, com uma nuance importante — existem **duas entidades "Organization" diferentes** no código:

| Entidade                       | Onde                                                                                                                    | Persistência                                                                                                      |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **Control-Plane Organization** | `apps/api/src/modules/control-plane/tenancy.repository.ts`                                                              | ✅ Real, Prisma/Postgres (desde ATLAS 46.19/46.21)                                                                |
| **Portal Organization**        | `apps/api/src/modules/portal-identity/portal-identity-store.ts:78` (`private organizations: OrganizationRecord[] = []`) | ❌ Em memória — array na classe, perdido a cada restart do processo (exceto a org demo, re-semeada no construtor) |

**A que importa para ativação de runtime é a Portal Organization, em memória.** `runtime-registration-store.ts:197` resolve a organização chamando `portalIdentityStore.findOrganizationByCode(input.organizationCode)` — não o repositório Prisma do Control Plane.

**Chaves de ativação (`ActivationKeyRecord`)** — também em memória: `runtime-registration-store.ts:54` (`private activationKeys: ActivationKeyRecord[] = []`), com decisão de escopo registrada no cabeçalho do próprio repositório Prisma de runtimes (`runtime-registration.repository.ts:11-14`):

> _"Activation keys, certificates, sessions, and runtime config remain in-memory in runtime-registration-store.ts — out of this sprint's scope (the mandate was specifically 'the Runtime registration itself must survive a restart', not every auxiliary record)."_

Ou seja: **a decisão de deixar isso em memória foi deliberada e documentada** (ATLAS 46.22), não um esquecimento — mas continua sendo verdade hoje que um restart do processo `apps/api` apaga toda chave de ativação emitida e toda organização de portal criada (exceto as seeds de demo). O próprio registro de Runtime (identidade do runtime) **já é** Prisma-backed desde ATLAS 46.22 — só os registros auxiliares (chaves, certificados, sessões, config) e a Portal Organization continuam em memória.
